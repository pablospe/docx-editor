# Roadmap

docx-editor lets an LLM agent propose edits to a Word document as tracked changes (redlines) and comments, then lets a human adjudicate them in Word. This file is the single source of truth for what is next, what is deliberately not planned, and what shipped.

Item numbers (`#N`) are stable identifiers, not GitHub issue numbers. PR titles cite them as `type: what changed (ROADMAP.md #N)`. Current release: **0.8.1** (2026-08-30).

## Where the library stands

- **Editing**: `replace`/`delete`/`insert_*`/`rewrite_paragraph` on hash-anchored paragraph refs (`P3#a7b2`), batched atomically with dry-run validation; `\n` in edit text is a tracked paragraph split; a `note=` on any edit anchors a rationale comment on its revisions.
- **Revisions, three tiers**: revision < group (one edit) < changeset (one batch call). Groups and changesets survive save/reopen by reconstruction from author + collision-bumped `w:date`. There is no fourth tier.
- **Honest on foreign documents**: editing inside another author's insertion preserves their proposal; `list_revisions` and every resolve verb handle `w:ins`/`w:del`/`w:moveFrom`/`w:moveTo`/`w:pPrChange`, and never claim success while other revision types remain (`list_unhandled_revisions`, `ResolveResult.unhandled`).
- **Text model**: the paragraph text map covers `w:t` and `w:tab` (one atomic `\t`); text-box content is excluded; only `word/document.xml` is edited.
- **Verification**: ~1,800 tests; a 77-file, 15-producer corpus (24 of them Word-authored redlines) runs weekly in CI through open → edit → save → reopen, a LibreOffice re-save survival check, and a PDF render.
- **Interfaces**: Python API, `docx-session` CLI (persistent Jupyter kernel with a JSON `eval`), and `skills/docx/SKILL.md` as the agent-facing contract.

## Design commitments (constraints every future item inherits)

- Refs are session-scoped: a paragraph's hash may change between sessions and after edits to it; consumers re-find, they never persist refs.
- `\n` means "tracked paragraph split". Any future visible element mapped into the text map must therefore use a character that is not `\n` (see #6).
- Replacing text inside your own pending insertion amends it in place (no new revision, `group_id=None`); undo is rejecting the amended insertion's group.
- The collision-bumped `w:date` per changeset is the join key for return-leg reconciliation (#69). Do not change the stamping scheme.
- Resolve verbs (`accept_all`, `reject_all`, …) report what they could not resolve rather than returning a clean count.
- Write only what LibreOffice and Word both keep on re-save; the corpus gate exists because an unknown element is dropped silently.

## Next

Ordered by value. Each is one board task and one PR unless noted.

### 6. `w:br` in the paragraph text map  [second half of #6; `w:tab` shipped in 0.8.1]

A run-level line break is still invisible to search, hashes and edit placement. It cannot map to `\n` (that means paragraph split — see commitments); candidate is a distinct atomic character (e.g. `\u2028`, LINE SEPARATOR) with the same boundary-only edit rules as tabs. Refs of affected paragraphs change, as they did for tabs.

### 63c. Refuse edits that land inside a field result

Only `w:instrText` is known to the library today. A `replace()` targeting text inside a TOC entry, `REF` or page-number field applies, and Word silently discards it on the next field update — the same silent-loss family already eliminated elsewhere. Minimum: detect that a match falls inside `fldSimple`/`fldChar` run ranges and refuse with a teaching error; better: a read-side field inventory. Board task `f812f113` exists in the backlog.

### 83. Inserted runs inherit formatting from the raw DOM, not the accepted view

Every path that decides which `rPr` a newly inserted run copies picks its boundary run with `getElementsByTagName("w:r")` — `_apply_paragraph_splits`'s `boundary_runs[-1]` and `_insert_ins_at_paragraph_start`'s `runs[0]` in `insert.py`, and `_rewrite_insert_at`'s empty-paragraph `runs[0]` in `batch.py`. That is document order, not the accepted view, so the "boundary" can be a run Word never shows: inside `w:del`, inside `w:moveFrom` (the moved-away source, which Word writes as plain `w:t`), or inside a `w:txbxContent` text box — the unfinished half of #65. A paragraph whose visible text is `Keep` plus a bold `w:moveFrom` run gives the inserted run bold; a bold paragraph carrying an italic text-box caption gives it italic. All of it reproduces before #79, with a plain `"A\nC"` split. Fix: take the boundary from `build_text_map`'s last (or first) visible position and walk to its `w:r` ancestor, which already excludes all three. Second defect on the same path: `get_rPr_xml` copies the boundary `rPr` verbatim, nested `w:rPrChange` included, so a new insertion carries a foreign author's tracked formatting change with its original `w:id` — `insert_after("body.", " A")` alone turns one unhandled revision into two. Sanitize the copy (drop `w:rPrChange`, as `_new_tail_paragraph` already does for the paragraph mark). Found by the multi-review of PR #95.

### 81. Workspace creation bypasses the unpack symlink guard

#77 made `unpack_document` refuse a symlinked nearest-existing ancestor of `output_dir`, but `Document.open(path, workspace_dir=<symlink>)` still extracts through the link: `workspace.py` creates the workspace directory before calling unpack, so the guard sees an existing real directory. Applying the same rule at workspace creation would refuse `workspace_dir="/tmp/<new>"` on macOS (`/tmp → private/tmp`), so it needs the same nearest-existing-ancestor rule *and* a decision on whether a user-chosen `workspace_dir` under a system symlink is legitimate (it is on macOS; document or resolve it). Found by the multi-review of PR #88. Also: `openspec/specs/structured-errors/spec.md:49` still describes an unscoped `replace()` call that the runtime rejects.

### 85. `_rejoin_paragraph` drops the tail paragraph's other revisions  [data loss]

Rejecting a paragraph-mark insertion migrates only the mark `w:ins` off the tail paragraph and then drops that paragraph's whole `w:pPr`, so another author's paragraph-mark `w:del`/`w:moveFrom`/`w:moveTo` and their `w:pPrChange` are destroyed — uncounted, unwarned, and with the merged paragraph's break left permanently untracked. Reproduces with no author filter, and is order-dependent within a single author: the same document returns 1 or 2 depending only on whether the mark-ins id sorts above the mark-del id. The `accept_all` docstring names only the `w:pPrChange` case. Fix: migrate the whole downstream mark set onto the surviving paragraph's mark `rPr`, since they all describe the break it now owns. Found by the multi-review of PR #96.

### 86. Historical marks inside change records list as live revisions

`list_revisions` and `_revision_element_index` walk with `skip_change_records=False` while `_unhandled_elements` uses `True`, so a revision mark recorded *inside* a change record is offered as adjudicable. `w:pPr/w:rPr/w:rPrChange/w:rPr/w:ins` is conforming (CT_ParaRPrOriginal admits EG_ParaRPrTrackChanges) and lists as a live insertion, and resolving it mutates the other author's change record; the nonconforming `w:pPrChange`-holding-`w:rPr` shape is worse — it merges two live paragraphs. Fix: have both walks pass `skip_change_records=True` and leave recorded marks to the honesty floor. Needs its own regression test. Found by the multi-review of PR #96.

### 89. `add_comment` cannot comment on a whole paragraph

`add_comment` requires anchor text that exists in the paragraph, so "this paragraph needs a citation" has no direct form. Two consumers invented the same workaround: anchor on the first 30 characters. Allow `add_comment(comment, paragraph=ref)` with no anchor text, anchoring the range on the paragraph's full content; an empty paragraph is a typed error, not a guess. Seen in the moonlion229 proofreading app.

### 91. `add_comment` crashes when `comments.xml` lacks the `w14` namespace

On a document that already ships a `word/comments.xml` whose root does not declare `xmlns:w14` (an empty comments part is enough), `add_comment` raises a raw `ExpatError: unbound prefix`: the comment fragment carries `w14:paraId` and is parsed against the existing root (`comments.py::_add_to_comments_xml`, `xml_editor.py::_parse_fragment`). Hit on the stock supply agreement from the Harvey LAB set used by docx-agent-bench; `note=` on edits goes through the same path and likely fails the same way. Fix: declare the namespaces the fragment needs on the existing root before inserting (comments, commentsExtended and friends), and audit every other fragment insert into a pre-existing part for the same assumption. A parse failure that still escapes must surface as a typed error, not `ExpatError`. Tests: a fixture with a namespace-poor `comments.xml`, for `add_comment`, `reply_to_comment` and a `note=` edit, plus the LibreOffice opens-clean gate.

### 92. Comments without `w14:paraId` cannot be replied to, resolved or deleted

`_load_existing_comments` skips any `w:comment` that carries no `w14:paraId`, so `reply_to_comment`, `resolve_comment` and `delete_comment` report "not found" for a comment that `list_comments()` returns. Every pre-existing comment in a document written by Word 2007, LibreOffice or Google Docs is in that state. Fix: mint a `paraId` for such a comment when a verb first needs one (and wire the extended parts), or make the three verbs work from `w:id` alone; either way a listed comment must be actionable. Found while planning #91.

### 93. A namespace prefix declared on a non-root ancestor breaks re-serialized runs

`rebuild_run_fragments` and the other `toxml()` round trips assume every prefix used in existing content is declared on the part's root. With `<w:p xmlns:foo="urn:foo"><w:r><foo:mark/>…`, a plain `replace` or `add_comment` raises on the unbound prefix (after #91: a typed `XMLError`). Declarations on the element itself, which is what Word writes for drawings, are fine; only a declaration on an intermediate ancestor breaks. Not seen in the corpus. Fix: carry the in-scope namespace declarations of the source element into the fragment wrapper. Related, from the review of #91: a `document.xml` root that binds `w14`, `w16du` or `w16cex` to a different URI now raises `XMLError` after the tracked nodes are in the DOM (main wrote into the wrong namespace silently); check the bindings before the edit starts. Found while planning #91.

### 94. Ambiguity errors say where the matches are  [0.8.4: fewer round trips]

`AmbiguousTextError` reports how many times the target matched and a paragraph preview, so the agent has to run a second search to learn which `occurrence=` it wants. Carry the matches on the error: for each, its `occurrence` index, `paragraph_ref` and a short window of surrounding text, capped (first N plus a count) so a common word cannot flood the output, and present in the session JSON error. The message should read as a pick-list. Seen in stetdoc, whose refusals list every match with its location.

### 95. Document-wide edits that refuse when the target is not unique  [0.8.4]

`replace`/`delete`/`insert_after`/`insert_before` need a paragraph ref, so every edit is find-then-edit: two calls where the agent already knows the text. Allow the edit verbs without `paragraph=` when the target occurs exactly once in the document; more than one match is `AmbiguousTextError` with the located list from #94, zero is `TextNotFoundError`, and nothing is written in either case. Add `expected_count=N` to the bulk forms (`find_all` + `batch_edit`, and any replace-all path): the call refuses, writing nothing, when the number of matches differs from what the caller stated. Design first: how this composes with hash-anchored refs (the safety those give must not be lost — a document-wide edit still returns the ref it touched) and with `occurrence=`.

### 96. Quote-insensitive matching

Contracts are full of typographic quotes and apostrophes; an agent types `"Term"` or `don't` with straight ones and gets `TextNotFoundError` on text that is visibly there. Match straight and curly forms of `'` and `"` as equivalent when locating text (`'` with U+2018/U+2019, `"` with U+201C/U+201D), in every locate path, while writing replacement text exactly as given. Decide and document: on by default or opt-in, and whether inserted text adopts the document's quote style (default: no, write what was passed). The match offsets must map back to the original characters so run splitting is unaffected.

### 97. Every error names the next call

Structured errors already carry fields; what they lack is a uniform, machine-readable `next` hint: the one call that usually resolves the situation (`HashMismatchError` → re-read the paragraph with `get_paragraph(i)`; `AmbiguousTextError` → pass `occurrence=`; `TextNotFoundError` → `find_all` or full text from `list_paragraphs_structured`; `RevisionError` on a duplicated id → `author=`). Add it to the exception base, the session JSON error, and the SKILL.md error table, one line per exception. No free-form advice: a short imperative naming a real call.

### 29. Computed list numbers ("7.2(a)")  [large; after the 0.8.4 batch]

Word computes clause numbers at render time from `numbering.xml`, the style chain and the list's running state, so "clause 7.2(a)" is not text in the file. `ParagraphLocation.list` gives only `(num_id, ilvl)`. An agent asked to "change clause 11.1" on an auto-numbered contract cannot find it; it worked on the docx-agent-bench contracts only because their numbers are typed as text. Compute the rendered label per paragraph (levels, start overrides, restarts, `lvlText` patterns, the common number formats), expose it on `ParagraphInfo`/`ParagraphLocation` and on search results, and allow lookup by label. Mark what is heuristic (legal numbering, custom formats, `w:numPicBullet`) rather than guessing. Design first; validate against real Word on the corpus. Promoted from Later on 2026-11-14: stetdoc ships this and it is the main capability gap for contract work.

### 98. Rejecting a split drops the tail's property change when the head has a numbering revision  [data loss]

Left as on main by #85. When the head paragraph's `w:numPr` holds a tracked revision (`w:ins` or `w:numberingChange`) and the tail carries a `w:pPrChange`, rejecting the split drops the tail's record, uncounted: the record only means something together with the tail's base properties, and adopting those replaces the head's `w:numPr`. Fix: refuse. `reject_revision`/`reject_group` raise a typed `RevisionError` naming the two revisions ("resolve one first") and leave the paragraphs unmerged; bulk `reject_all` leaves the split pending, uncounted, and says so. Design first: the bulk half changes what `reject_all()` promises and touches `_resolve_all`'s ordering and termination, the code behind the 42 GB incident.

### 99. Rejecting a `w:pPrChange` deletes a numbering revision in the same paragraph  [data loss]

`_restore_paragraph_properties` replaces every base property with the recorded ones. A `w:numPr` holding a pending `w:ins`/`w:numberingChange` is not in the record, so it goes, uncounted: a paragraph with numbering revision 21 and its own `w:pPrChange` 11, `reject_revision(11)` leaves neither. Pre-existing; measured while reviewing #85. Fix: keep a revision-bearing `w:numPr` across the restore, or refuse. Check the meaning against Word before choosing.

### 100. Rejecting a split looks only at the next element sibling for the tail

With a `w:bookmarkEnd`, `w:commentRangeEnd`, `w:moveFromRangeEnd` or similar between the two paragraphs, or the tail wrapped in `w:sdt`, rejecting the split removes only the mark, leaves an untracked paragraph break, and returns True. Pre-existing; found by the review of #85. Fix: skip body-level range markup when locating the tail, look inside `w:sdt`, and refuse with a typed error when no tail can be found rather than reporting success.

### 101. A `note=` edit whose note cannot be attached stays applied and raises

`_attach_notes` runs after the edit is in the DOM. When the comment part is rejected (`XMLError`), the caller gets an exception instead of an `EditResult`, so it has no `group_id` to undo with, and a retry applies the edit twice. `batch_edit` rolls back; a single edit does not. Fix: either check the comment parts before the edit starts in every verb that takes `note=`, or keep the edit and report the note through the existing `UnanchoredNoteWarning`. Found by the review of #91.

### 69. Return-leg reconciliation: which changesets survived?  [design]

The product loop is agent proposes → human adjudicates in Word → document comes back; accepted revisions become plain text, rejected ones vanish, and there is no way to ask "which of my changesets survived?". A propose-time-vs-current compare keyed on changeset `w:date` + content. Design first; large.

Design constraint (2026-09): the library cannot assume the caller still has the proposed file. In a synced store (OneDrive, SharePoint, Drive, a DMS) there is one live document and adjudication overwrites the only evidence. So `save()` must retain the propose-time state itself — a snapshot or a compact manifest of changeset fingerprints (join key, accepted-view and rejected-view text, anchors) — and reconciliation reads that. The store's version history is the fallback; an explicit two-file `reconcile(sent, returned)` stays as the email case. With neither snapshot nor history the question is unanswerable, and the API must say so rather than guess.

## Later (demand-gated — revisit when a named consumer asks)

- **74. Author moves.** The library never writes `w:moveFrom`/`w:moveTo`; a move through the API is a delete plus an insert (one changeset when done in one batch call), which Word shows as two revisions rather than one green move pair. Emitting a real move pair when a batch deletes text and inserts the identical text elsewhere is now feasible on #68's machinery (range marks, pairing by `w:name`). No consumer has asked.
- **30. Container parts** (headers/footers/footnotes/endnotes): multi-part refs (`H1:P2#hash`), per-part editors, tracked-change routing. Stage (a) read-only enumeration, (b) locations, (c) tracked edits. Zero requests across four dogfood rounds; the failure mode is a visible miss, not silent corruption.
- **MCP server** (PR #7, parked): persistent document caching behind an MCP interface; the `docx-session` kernel covers the same need today.

## Out of scope — deliberate refusals

- **Redaction.** Actively dangerous here: a tracked-changes library preserves history by design, so pseudo-redaction that leaves text in `w:del`, prior versions, or metadata is a liability generator. Permanent refusal.
- **Word automation suite**: table/image/style/section authoring, TOC and field authoring, content controls, mail merge, COM/live-Word integration. Cell *text* edits already work, which is the redline case; the rest enlarges the corruption surface of files shared with external parties.
- **Regex find/replace.** The consumer is an LLM that reads text and emits exact strings; regex adds span-vs-revision-context semantics and a footgun surface for zero demonstrated demand.
- **Two-arbitrary-document diff.** The domain version already exists — `list_revisions` markup view, `get_text`/`get_original_text`, rewrite diffing. The valuable cousin is #69.
- **Read-only schema validators.** The real contract is "opens in Word with zero repair prompts"; a schema check cannot predict that. The corpus gate is the honest version.
- **Text boxes as an editing surface** — only the exclusion fix (#65) shipped; box text is invisible, not half-editable.

## How this roadmap is set

CodeRabbit reviews every PR; its inline Critical/Major/Potential-issue comments are triaged before merge (an audit on 2026-08-30 of 261 unread comments produced #75–#80). Batches come from evidence, not ideas: four dogfooding rounds (consumer-persona agents driving the library from `SKILL.md` alone, adversarial error QA, token economics, scale), the corpus revision census (which types real producers emit), and a clean-room comparison against KitchenSink4Word (test *names* only — its code is PolyForm-NC and unusable). A finding becomes an item here, an item becomes a PR citing it, and a release closes a theme.
